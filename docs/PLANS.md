# 計画の書き方

大きめの変更（複数のファイルにまたがる変更や、振る舞いを変える変更）は、着手の前に計画を書く。
計画は `YYYY-MM-DD-<名前>.md` の名前で、進行中なら `docs/exec-plans/active/` の直下に、完了したら `docs/exec-plans/completed/` の
直下に置く（次の「置き場所と名前」）。

## 置き場所と名前

- 進行中の計画は `docs/exec-plans/active/` の直下に、完了した計画は `docs/exec-plans/completed/` の直下に置く。
  `bash scripts/harness/check-docs.sh` は、この 2 つのディレクトリの直下だけを見る（さらに下のディレクトリは見ない）。
- 作業を終えたら、「結果と振り返り」の節を書いてから、計画を `completed/` へ移す。
- 計画の状態（進行中、完了）は、置いたディレクトリで表し、ファイルの中には書かない。
- 名前が `.acceptance.md` で終わるファイルは、受け入れ確認の記録（下の「受け入れ確認の記録」）である。それ以外の `.md` は、
  すべて計画とみなして、下の「必須の節」が揃っているかを確かめる。

## 必須の節

計画には、次の 8 つの見出しを、この文字列のまま置く。書くことがまだ無い節も、見出しは残す。
`bash scripts/harness/check-docs.sh` は、この一覧の各行の、バッククォートで囲んだ見出しを読み取って照合する。一覧の行の形
（番号、ピリオド、空白、バッククォートで囲んだ見出し）を変えるときは、`scripts/harness/check-docs.sh` も直す。

1. `## 作業の場所`: 作業するブランチの名前。パスは書かない。
2. `## 目的`: 何を、なぜ変えるか。製品の仕様があるときは、そのパス（`docs/product-specs/<名前>.md` の形）も書く。
3. `## 検証（完了の条件）`: 終わったと言える条件と、その確かめ方。書式は下の「検証の節の書式」に従う。
4. `## 手順`: 作業の順序。
5. `## 進捗`: 終えた手順と日付、残っている手順。
6. `## 発見`: 作業の途中で分かった、前提と違う事実。
7. `## 判断の記録`: 途中で決めたことと、その理由。
8. `## 結果と振り返り`: 閉じるときに、何ができて何が残ったかを書く。

## 検証の節の書式

次の 1 行に書いた日付以降の日付をファイル名に持つ計画（ファイル名が日付で始まらない計画も含む）を、新しい書式の計画と呼ぶ。
新しい書式の計画は、検証の節に、基準ごとの見出しと確かめ方の行を置く。

新しい書式の適用開始: 2026-10-09

- 基準ごとに `### <識別子> <題>` の見出しを置く。識別子は、計画の中で振る `V<数字>`（`V1`、`V2` など）か、製品の仕様の
  受け入れ基準の識別子（`<略号>-<数字>` の形。`docs/product-specs/README.md`）とする。識別子に空白を含めず、同じ計画の中で
  重ねない。
- 見出しの下に、`- 前提:`、`- 操作:`、`- 期待する結果:`、`- 確かめ方:` の行を置く。
- 確かめ方の行は、行の頭から `- 確かめ方: <値>` の形のまま書き（半角のコロンと空白。字下げや別の箇条書きの記号を使わない）、
  各見出しの下にちょうど 1 行置く。値は「自動テスト」「受け入れ確認」「人が確認」のどれか 1 語だけを書く。値の後ろに、
  試験の名前やコマンドなどを書き足さない。試験の名前やコマンドは `- 操作:` や `- 期待する結果:` の行に書く。
- 「受け入れ確認」は、動いているアプリを、実装した本人とは別の受け入れ確認の担当が操作して確かめることを指す。
  確かめ方が受け入れ確認の基準には、`- 対象ファイル:` の行に、確かめる対象のファイルを並べる。
- 受け入れ確認の基準は、表ではなく、見出しと確かめ方の行で書く。
- ``` で囲んだコードブロックの中の行は、基準にも確かめ方にも数えない。コードブロックは必ず閉じる。
- 計画が引く製品の仕様があるときは、目的の節に、引く仕様のパスをリポジトリの根からの `docs/product-specs/<名前>.md` の形で
  書く（仕様が 2 つ以上なら並べる）。検証の節では、仕様の受け入れ基準を識別子で引き、仕様の文面は書き写さない。計画が引く
  のは、進行中の計画では目録の状態が `approved` の仕様だけで（承認の前に計画を書かない）、完了した計画では `approved` か
  `archived` の仕様である（完了した後に仕様が新しい仕様に置き換わって `archived` になっても、過去の計画を失敗にしないため）。
  仕様の書式と目録の正本は `docs/product-specs/README.md` である。仕様の無い作業（不具合の修正、内部の整理）では、
  基準を `V<数字>` で、この節に直接書く。
- `bash scripts/harness/check-docs.sh` は、`active/` と `completed/` の新しい書式の計画について、仕様の引き方を次のとおり
  失敗にする。
  - `V<数字>` でない識別子が、どの仕様の受け入れ基準にも無い（仕様の置き場が無ければ、`V<数字>` でない識別子はすべて失敗）。
  - 目的の節に書いた仕様と、検証の節の識別子の所属先の仕様の状態が、進行中の計画では `approved` でない、完了した計画では
    `approved` でも `archived` でもない。
  - 仕様の識別子を引くのに、目的の節に仕様のパスが無い。目的の節に書いた仕様のパスが目録に無い。
  - 識別子の所属先の仕様が、目的の節に書いた仕様のどれでもない。
- 検証の節の中の `###` の見出しは、すべて基準として数えられる。検証の節では、基準以外に `###` の見出しを使わない。

`bash scripts/harness/check-docs.sh` は、`completed/` にある、新しい書式の計画では、検証の節について次を失敗にする。
進行中の計画は、この書式の崩れを検査しない。

- 確かめ方の行が、どの `### <識別子>` の見出しの下にも無い。
- 見出しの下に確かめ方の行が無い、または 2 行以上ある。確かめ方の値が上の 3 つのどれでもない。
- 識別子が重複している。識別子の無い見出しがある。
- 「確かめ方」の語の後に `:` か `：` が続くのに、上の形に一致しない行（全角のコロン、字下げ、別の箇条書きの記号など）。
- 「確かめ方」と「受け入れ確認」の両方を含むのに、上の形に一致しない行（コロンの無い行など）。
- 「受け入れ確認」を含む表の行。地の文と、ほかの項目の行（`- 期待する結果:` など）で受け入れ確認に触れるだけの行は対象にしない。
- 基準の見出し（`### <識別子> <題>`）が 1 つも無い。
- 閉じていないコードブロック（``` の行の数が奇数）。

例:

```markdown
### V1 文字の大きさを「大」にすると、一覧の文字が大きくなる

- 前提: 一覧が標準の文字の大きさで表示されている。
- 操作: 文字の大きさの切り替えで「大」を選ぶ。
- 期待する結果: 一覧の各項目の題が、標準より大きい文字で表示される。
- 確かめ方: 受け入れ確認
- 対象ファイル: `src/list/view.ext`
```

## 受け入れ確認の記録

確かめ方が受け入れ確認の基準を、受け入れ確認の担当が確かめた結果の記録。担当は、このファイルだけに書き込む。

### 置き場と名前

- 計画と同じディレクトリに、`<計画のファイル名から .md を除いたもの>.acceptance.md` の名前で置く
  （例: `2030-01-15-list-font-size.md` の記録は `2030-01-15-list-font-size.acceptance.md`）。
- 計画を `completed/` へ移すときは、記録も同じ変更で移す。
- `bash scripts/harness/check-docs.sh` は、新しい書式の計画のうち `completed/` にあるものについて、受け入れ確認の基準が
  あるのに記録が無い、判定に数える実行が 1 件も無い基準がある、基準ごとの最新の結果が「合格」でない、記録が下の「書式」の
  決まりに合わない、のいずれかを失敗にする。あわせて、`active/` と `completed/` のどちらでも、同じ名前の計画が無い記録、
  計画と別のディレクトリにある記録、絶対パスの形を含む記録を失敗にする。

### 書式

確かめるたびに、ファイルの末尾に `## 実行 <番号>` の節を 1 つ足す。

- `## ` の見出しは `## 実行 <番号>` だけを使う。番号は 1 から始め、欠けずに 1 ずつ増やす。実行の節は 1 つ以上置く。
- 各実行の節に、次の 8 つの行をちょうど 1 行ずつ置く: `- 日時:`、`- 確かめた者:`、`- 元のコミット:`、`- 分岐元:`、
  `- 確かめた対象:`、`- 基準外の所見:`、`- 未確認の範囲:`、`- 全体:`。行の頭の `- ` と、項目の名前の後の `: ` は変えない。
  `- 確かめた対象:` 以外は、同じ行に値を書く（`- 確かめた対象:` の値は、その下の字下げした行に並べる）。無いときも
  「なし」と書き、行を省かない。
- `- 全体:` の値は `合格`、`不合格`、`未確認` のどれか 1 語。
- 各実行の節に `- 基準 <識別子>: <結果>` の行を 1 つ以上置き、各行の下に、字下げした `- 証拠: <値>` の行を置く。結果は
  `合格`、`不合格`、`未確認` のどれか 1 語だけを書く。
- ``` で囲んだコードブロックは必ず閉じる。コードブロックの中の行は、記録に数えない。
- `- 確かめた者:` には、確かめた担当の名前を書く。判定に数えるのは `app-evaluator` の実行だけで、ほかの名前の実行
  （実装した本人の自己確認など）は記録に残してよいが、合否の判定には数えない。
- 確かめられなかった基準は `未確認` とし、全体を合格にしない。1 件でも `不合格` があれば全体を `不合格` とし、その基準の下に
  再現の手順と、分かれば該当のコードの場所を書く。
- 一部の基準だけを確かめ直した実行には、確かめ直した基準の行だけを書く。基準ごとの判定には、判定に数える実行のうち、その
  基準の行を持つ最も後の実行の結果を使う。
- 基準外の所見には、基準に当たらないが見つけた問題を書く。無ければ「なし」と書く。
- 前提・操作・観察した結果の行も、基準ごとに書く（検査はしないが、再現と見直しに要るため）。

```markdown
# 受け入れ確認の記録: 2030-01-15-list-font-size

## 実行 1

- 日時: 2030-01-15 14:05（日本時間）
- 確かめた者: app-evaluator
- 元のコミット: <確かめた時点の git rev-parse HEAD の値>
- 分岐元: <git merge-base HEAD origin/main の値>
- 確かめた対象:
  - `src/list/view.ext` <git hash-object の値> <状態>
- 基準 V1: 合格
  - 前提: 一覧を標準の文字の大きさで表示した。
  - 操作: 文字の大きさの切り替えで「大」を選んだ。
  - 観察した結果: 一覧の各項目の題が、標準より大きい文字で表示された。
  - 証拠: 画面の本文の抜き書き。スクリーンショット v1.png（一覧の全体が写っている）。
- 基準外の所見: なし
- 未確認の範囲: Figma との照合（照合する対象が無い）
- 全体: 合格
```

### 確かめた対象の特定

確かめる前に、次の手順で対象を特定し、「元のコミット」「分岐元」「確かめた対象」の行に書く。後で、どの内容を確かめたかを
コミットと比べられるようにするためである。

1. 元のコミット: 確かめる時点の `git rev-parse HEAD` の値。
2. 分岐元: `git merge-base HEAD origin/main` の値。作業のブランチが既定のブランチから分かれたコミットで、対象の範囲の起点にする。
3. 対象のファイル: 基準の `- 対象ファイル:` に書いたもの。計画が書かないときは、`git diff --name-only <分岐元>` と
   `git ls-files --others --exclude-standard` の出力の和。
4. 対象のファイルごとに、パスの順に、作業ツリーの内容の `git hash-object -- <パス>` の値（ファイルが無ければ「なし」）と、
   `git status --porcelain=v1 --untracked-files=all -- <パス>` の出力の先頭の 2 文字（出力が空なら「変更なし」）を書く。

### 書いてはならないもの

- 絶対パス（ホームの下、一時ディレクトリの下のどちらも）。アカウント名が入るためである。パスはリポジトリの根からの
  相対で書く。
- 認証情報（パスワード、トークン、Cookie）、個人のメールアドレス、アカウントの識別子。
- スクリーンショットそのもの。スクリーンショットはリポジトリの外の一時ディレクトリに置き、記録にはファイル名と、
  写っているものだけを書く。

### 追記だけで書き換えない

- 記録には実行の節を末尾に足すだけで、前の実行の記述を書き換えたり消したりしない。誤りに気づいたら、新しい実行の節で
  確かめ直し、所見にその旨を書く。
- 担当は、書いた後の記録の全体のバイト数（`wc -c < <記録>`）と sha256（`shasum -a 256 < <記録>`）を報告する。
  過去の各回の（バイト数, sha256）について、記録の先頭のそのバイト数の部分（`head -c <バイト数> <記録>`）の sha256 が、
  その回に報告した値と一致すれば、その回の範囲は書き換わっていない。
